# Объединённый roadmap: RAG-чат на FastAPI

**Один сквозной проект, который чинит FastAPI/SQLAlchemy и достраивает LLM-слой одновременно.**

Проект: **«Корпоративный ассистент по документам»** — RAG-чат. Загрузил документы → задал вопрос → получил ответ по ним со стримингом и цитатами. Это буквально то, что описано в LLM-вакансии, и то, что не стыдно кинуть в отклик.

---

## Как это работает

Каждый этап даёт **работающий инкремент** — на любом можно остановиться и показывать. FastAPI/SQLAlchemy-теория подтягивается не отдельно, а ровно там, где она нужна для текущей LLM-фичи. Ты стряхиваешь пыль на живом коде.

Обозначения источников:
- **[F]** — FastAPI + SQLAlchemy recovery
- **[L]** — Python + LLM/AI roadmap

Приоритет — быстрее собрать сквозной скелет, потом наращивать. Тесты + mypy держим с самого начала, но не блокируемся на 100% покрытии на ранних этапах.

## Этап 0. Скелет сервиса (0.5–1 день)

**Цель:** живой FastAPI-сервис, который отвечает, с правильной структурой с первого дня — чтобы потом не переписывать.

**FastAPI-теория, которую закрываешь:**
- [F] Модуль 1 — основа, роутинг, async vs sync, path/query/body
- [F] Модуль 6 (структура) — сразу разложи по слоям, не жди, пока разрастётся

**Задания:**
- [F] 1.1 — health + echo, проверить через `/docs`
- [F] 1.3 — **сделай обязательно и осознанно.** Два эндпоинта с `time.sleep(3)`: `async def` vs `def`, дёрни по 3 параллельных запроса, объясни письменно разницу. Это фундамент под весь LLM-слой: стриминг, очередь, backpressure — всё про то, чтобы не заблокировать event loop.
- [F] 6.2 — сразу разложи проект: `main.py` тонкий, `api/routers/`, `db/session.py`, `schemas/`, `crud/`, `services/`, `core/config.py`

**Готово, когда:** сервис поднимается, `/docs` открывается, структура разложена, ты можешь объяснить, почему блокирующий вызов в `async def` — это катастрофа.

## Этап 1. Первый разговор с LLM (1–2 дня)

**Цель:** сервис реально ходит в LLM по HTTP и отвечает. Это ядро всей ниши.

**LLM-теория:**
- [L] 1.1 — OpenAI-совместимый API (`/v1/chat/completions`, роли, параметры, `finish_reason`, `usage`)

**FastAPI/Pydantic-теория под это:**
- [F] Модуль 2 — Pydantic v2, разделение Create/Read, `response_model`. Тебе это нужно, чтобы типизировать запрос/ответ к LLM и наружу.

**Задания:**
- [L] Приложение к секции 1 — **подними мок LLM-сервер** (`mock_llm.py`, `uvicorn mock_llm:app --port 8001`). Занимайся без реальной LLM.
- [L] 1.1 — async-клиент к `chat/completions` на `httpx.AsyncClient`, возвращает dataclass (`content`, `prompt_tokens`, `completion_tokens`, `finish_reason`), логирует предупреждение при `finish_reason == "length"`, заворачивает ошибки в `LLMError`. Проходит mypy, есть тест с моком.
- [F] 2.1 — три модели одной сущности (примени к сообщению чата: `MessageCreate` / `MessageRead`)
- Свяжи: FastAPI-эндпоинт `POST /chat`, который принимает сообщение и возвращает ответ мок-LLM.

**Готово, когда:** `POST /chat` → сервис ходит в мок → возвращает типизированный ответ. Кейс `finish_reason: length` обработан.

## Этап 2. Стриминг (1–2 дня)

**Цель:** ответ печатается по токенам, как в ChatGPT. Ты — и потребитель SSE (от LLM), и производитель (во фронт).

**LLM-теория:**
- [L] 1.2 — SSE, `delta` vs `message`, склейка `delta.content`, `data: [DONE]`

**FastAPI-теория под это:**
- [F] Модуль 3 (DI) — зависимости через `yield` для управления ресурсом (соединением к LLM), `Annotated`-паттерн

**Задания:**
- [L] 1.2 — стриминговый клиент: `client.stream(...)`, `response.aiter_lines()`, парсинг SSE, обработка чанка без `content` (первый чанк — только роль, не должно быть `KeyError`), `collect(stream)` для тестов
- [F] 3.1 — общий параметр пагинации через зависимость (разминка на DI)
- [F] 3.2 — ресурс через `yield` с корректным закрытием в `finally` даже при исключении
- Свяжи: FastAPI-эндпоинт со `StreamingResponse`, пробрасывающий SSE-поток от LLM во фронт.

**Готово, когда:** `curl` к твоему стриминг-эндпоинту печатает ответ по кусочкам. Разрезанный между чанками SSE-ивент не ломает парсинг.

## Этап 3. Данные: документы и история в БД (2–3 дня)

**Цель:** документы, пользователи и история диалога живут в БД. Здесь ты закрываешь **главную дыру recovery-гайда — SQLAlchemy-запросы.**

**FastAPI/SQLAlchemy-теория (большой блок):**
- [F] Модуль 4 — модели 2.x стиля (`Mapped`, `mapped_column`), async-движок, `expire_on_commit=False` и почему без него `MissingGreenlet`
- [F] Модуль 5 — **это твой ключевой модуль.** `select()`, `scalars`/`scalar_one`/`mappings`, джойны, агрегации, N+1 и `selectinload`/`joinedload`, insert/update/delete, upsert

**Задания:**
- [F] 4.1 — первые модели в стиле 2.x
- [F] 4.2 — async-сессия как зависимость на SQLite (`sqlite+aiosqlite`), `POST` с `commit` + `refresh`
- [F] 5.1 — select и scalar (получить по полю, все по условию, count)
- [F] 5.2 — JOIN + агрегация (например: сколько сообщений в каждом диалоге)
- [F] 5.3 — **поймай и убей N+1** с `echo=True`, перепиши через `selectinload`, подтверди по логам, что запросов стало два. Плюс оконная функция.
- Свяжи: модели `User`, `Document`, `Chat`, `Message`. История диалога сохраняется и подгружается для многоходового контекста.

**Готово, когда:** диалог персистится, история подгружается без N+1, ты можешь объяснить `selectinload` vs `joinedload` вслух.

## Этап 4. RAG-ядро: индексация и поиск (3–5 дней)

**Цель:** сердце вакансии. Режем документы, эмбеддим, ищем — руками, без LangChain.

**LLM-теория (большой блок):**
- [L] 2.1 — зачем RAG, фазы индексации и запроса
- [L] 2.2 — чанкинг (overlap, по структуре, метаданные для цитирования)
- [L] 2.3 — эмбеддинги (cosine, `sentence-transformers`, префиксы e5/bge, одна модель для индекса и запроса)
- [L] 2.4 — векторный vs лексический поиск, гибрид, RRF

**Задания:**
- [L] 2.1 — чанкинг с перекрытием (считай в токенах через `tiktoken`)
- [L] 2.2 — загрузка PDF/txt/md с номером страницы в метаданных
- [L] 2.3 — `Embedder` на `sentence-transformers` (`all-MiniLM-L6-v2` → `multilingual-e5-small` для русского), автопрефиксы, батчинг, тест `cosine("кошка","котёнок") > cosine("кошка","самолёт")`
- [L] 2.4 — `InMemoryVectorStore` руками через numpy matrix @ query (прочувствуй, почему не цикл)
- [L] 2.5 — BM25 (сначала `rank-bm25`, потом формула сама)
- [L] 2.6 — гибрид с RRF руками
- [L] 2.7 — rerank (cross-encoder), схема retrieve top-50 → rerank top-5

**Готово, когда:** можешь загрузить документ, найти по нему релевантные чанки гибридом, и объяснить, где dense промахивается, а BM25 спасает.

## Этап 5. Генерация с цитатами и контролем галлюцинаций (2–3 дня)

**Цель:** заставить модель отвечать по контексту, ссылаться на источники и не выдумывать. Это отличает игрушку от продакшена.

**LLM-теория:**
- [L] 3.1 — сборка контекста (бюджет токенов, lost in the middle, маркеры источников, дедуп)
- [L] 3.2 — RAG-промпт, контроль галлюцинаций, отделение инструкций от данных
- [L] 3.3 — оценка качества (Recall@k, MRR, faithfulness)

**FastAPI-теория под это:**
- [F] Модуль 6 (ошибки) — кастомные исключения и обработчики; пригодятся для «не нашёл релевантного»

**Задания:**
- [L] 3.1 — сборщик контекста с бюджетом токенов и дедупом
- [L] 3.2 — `RAGPipeline`: retrieve → context → prompt → LLM, со стримингом и цитатами `[Источник N]`
- [L] 3.3 — верификация цитат (ловит выдуманный `[Источник 99]`)
- [L] 3.4 — порог релевантности и честный отказ
- [F] 6.1 — кастомная 404 (`ItemNotFound` в CRUD)
- [L] 3.5 — **мини-фреймворк оценки RAG.** Золотой набор 15–20 пар, Recall@k и MRR, сравнение dense/BM25/гибрид/+rerank таблицей. Это золото на собесе: «как вы оцениваете качество RAG?»

**Готово, когда:** на вопрос по документам — ответ с цитатами; не по теме — честное «не нашёл»; у тебя есть таблица метрик, которой обоснуешь конфигурацию.

**⚑ Здесь у тебя уже полноценный сквозной RAG-чат. Это минимальный portfolio-ready срез — можно начинать откликаться.**

## Этап 6. Продакшн-надёжность LLM-слоя (2–3 дня)

**Цель:** защитить медленную LLM от перегрузки. Здесь твой highload-опыт из Tenzor ложится идеально.

**LLM-теория:**
- [L] 1.3 — таймауты, ретраи с backoff, backpressure, очередь, circuit breaker

**FastAPI-теория под это:**
- [F] Модуль 6.3 — единый формат ошибок + middleware + логирование с request-id

**Задания:**
- [L] 1.3 — таймауты (connect/read раздельно) и ретраи с экспоненциальным backoff (только на сетевых, 429, 503; не на 4xx)
- [L] 1.4 — `LLMGateway` с `asyncio.Semaphore`, метрики в памяти, `queue_timeout`
- [L] 1.5 — circuit breaker (CLOSED/OPEN/HALF_OPEN)
- [F] 6.3 — middleware ловит необработанные исключения, логирует с uuid request-id, отдаёт единый JSON без трейса; `RequestValidationError` в тот же формат

**Готово, когда:** 10 запросов при `max_concurrency=2` не роняют LLM; при стабильных сбоях срабатывает предохранитель; ошибки отдаются единым форматом.

## Как подавать в портфолио

Из [L] секции 8 — это читают внимательнее кода:
- **Чистый README:** архитектурная схема, как запустить, gif чата.
- **Раздел «инженерные решения»:** почему гибридный поиск, как боролся с галлюцинациями, как устроена очередь к LLM.
- **Раздел «оценка качества»:** метрики RAG из этапа 5.
- **Истории, не факты:** не «я знаю RAG», а «retrieval возвращал мусор на точных терминах → добавил BM25 через RRF → recall@5 вырос с X до Y».
- **Опирайся на бэкенд:** твои 11 лет и highload — козырь. Подавай себя как сильного бэкендера, добравшего LLM-специфику.
